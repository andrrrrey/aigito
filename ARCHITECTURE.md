# Архитектура проекта AIGITO

Документ объясняет, как устроен AIGITO «изнутри»: из каких частей он состоит, как
они общаются друг с другом, и — самое важное — **почему** разработчики приняли
именно такие решения. Написано простым языком, чтобы было понятно даже без
глубокого погружения в код.

---

## 1. Что это вообще такое

**AIGITO** — это платформа голосового (и опционально видео-) AI-аватара для
офлайн-бизнеса. Представьте планшет или большой экран в стоматологии, кафе или
салоне. На экране — «лицо» виртуального помощника. Клиент подходит, говорит
вслух свой вопрос («Сколько стоит чистка зубов?»), и аватар голосом отвечает,
опираясь на базу знаний конкретной компании.

Ключевая идея: **один и тот же движок обслуживает много разных компаний**. Каждая
компания через админ-панель загружает свои документы, настраивает голос,
характер и поведение аватара. Это называется **мультитенантность** (один сервис —
много независимых «арендаторов»).

Из этого вытекают три главных требования, которые объясняют почти все
архитектурные решения:

1. **Реальное время.** Человек не будет ждать ответа 10 секунд — нужна обработка
   речи «на лету».
2. **Изоляция компаний.** Данные одной компании никогда не должны попасть к
   другой.
3. **Простота развёртывания.** Платформу должны уметь поставить на обычный VPS за
   пару часов по инструкции, без DevOps-команды.

## 2. Вид с высоты птичьего полёта

Система состоит из нескольких независимых сервисов, каждый в своём
Docker-контейнере. Вот как они связаны:

```
                        Браузер (планшет/экран)
                                  │
                          ┌───────▼────────┐
                          │     NGINX      │  ← единая точка входа, SSL
                          └───┬────┬───┬───┘
            /admin /kiosk     │    │   │ /api        /rtc (WebSocket)
                              │    │   │                  │
                   ┌──────────┘    │   └────────┐         │
                   ▼               ▼            ▼         ▼
              Статика       Статика       ┌─────────┐  ┌──────────┐
              (админка)     (киоск)       │ FastAPI │  │ LiveKit  │
                                          │ Backend │  │  Server  │
                                          └────┬────┘  └────┬─────┘
                                               │            │
                                               │       ┌────▼──────┐
                                               │       │  Agent    │ ← «мозг» аватара
                                               │       │ STT→LLM→TTS│
                                               │       └────┬──────┘
                          ┌────────────────────┼────────────┤
                          ▼                    ▼            ▼
                   ┌────────────┐       ┌────────────┐  ┌────────┐
                   │ PostgreSQL │       │   Qdrant   │  │ Redis  │
                   │  (данные)  │       │  (вектора) │  │ (кэш)  │
                   └────────────┘       └────────────┘  └────────┘
```

Главное, что стоит понять: **есть два совершенно разных «пути» данных**.

- **Путь управления** (синхронный, обычный HTTP): админ заходит в панель,
  загружает документы, меняет настройки. Это идёт через `Backend` → `PostgreSQL`.
- **Путь разговора** (реального времени, WebRTC): клиент говорит с аватаром. Это
  идёт через `LiveKit` → `Agent`. Здесь backend почти не участвует — он только
  выдаёт «пропуск» (токен) в начале.

Это разделение — **осознанное и центральное решение**. О нём ниже.

## 3. Из каких частей состоит система

### 3.1. NGINX — швейцар на входе

Всё внешнее общение идёт через один Nginx. Он:

- завершает SSL (HTTPS), чтобы остальным сервисам не нужно было думать о
  сертификатах;
- по URL решает, куда направить запрос: `/admin/` и `/kiosk/` — это статические
  файлы (HTML/JS/CSS), `/api/` — на backend, `/rtc` — на LiveKit (WebSocket);
- раздаёт фронтенд напрямую (статику), не нагружая Python.

**Почему так:** иметь единую точку входа проще и безопаснее — наружу торчит
только один сервис, один домен, один сертификат. Внутренние сервисы (PostgreSQL,
Qdrant, backend) не доступны из интернета напрямую.

Любопытная деталь: админка отдаётся с заголовком `X-Frame-Options: DENY` (нельзя
встроить в `<iframe>` — защита от кликджекинга), а киоск, наоборот, разрешено
встраивать на сторонние сайты — чтобы компания могла вставить аватар к себе на
страницу.

### 3.2. Frontend — два простых интерфейса на ванильном JS

- **`frontend-kiosk/`** — то, что видит клиент: «лицо» аватара, кнопка «начать
  разговор», субтитры.
- **`frontend-admin/`** — кабинет компании: загрузка документов, настройки голоса
  и характера, аналитика диалогов.

**Почему ванильный JavaScript, а не React/Vue?** Это сознательный выбор в пользу
простоты. Интерфейсы небольшие, основная сложность — не в UI, а в работе с
WebRTC и аудио. Отсутствие сборки (`npm build`) означает: правишь файл — и он
сразу раздаётся Nginx, никаких пайплайнов. Для киоска, который должен надёжно
работать на дешёвом планшете годами, минимализм — это плюс.

В `app.js` киоска видно много «бытовой» логики реального железа: разблокировка
автовоспроизведения аудио по клику (браузеры запрещают звук без жеста
пользователя), полноэкранный режим с учётом особенностей iOS Safari,
автоотключение по тишине (idle timeout), таймер демо-режима.

### 3.3. Backend (FastAPI) — панель управления

Это классический REST API на Python (FastAPI + SQLAlchemy 2.0 в асинхронном
режиме). Он отвечает за всё, что **не** про живой разговор:

- регистрация/вход компаний (JWT-аутентификация);
- хранение настроек компании;
- загрузка документов и их превращение в вектора (ingestion);
- аналитика — какие были диалоги, сколько минут наговорили;
- выдача токена для подключения киоска к LiveKit.

Backend разбит на модули по бизнес-смыслу (так называемая «вертикальная нарезка»):

```
backend/
├── auth/        — регистрация, вход, JWT
├── companies/   — настройки компании
├── knowledge/   — база знаний + векторизация
├── analytics/   — статистика диалогов
├── kiosk/       — выдача LiveKit-токенов, демо-режим
├── admin/       — суперадмин (управление всеми компаниями)
└── alembic/     — миграции БД
```

**Почему нарезка по доменам, а не по типам (отдельно все модели, отдельно все
роутеры)?** Так весь код одной фичи лежит рядом: модель, схемы, эндпоинты
`knowledge` — в одной папке. Добавляешь новую фичу — добавляешь папку, не трогая
остальные. Это легче читать и сложнее сломать.

**Почему всё асинхронное (`async`)?** Backend много времени ждёт: ответа от
PostgreSQL, от OpenAI, от Qdrant. Асинхронный код позволяет одному процессу
обслуживать много запросов одновременно, не простаивая в ожидании. Для I/O-bound
сервиса (а это именно он) — это правильный выбор.

### 3.4. Agent (LiveKit Agents) — настоящий «мозг» аватара

Это самая интересная часть. `agent/` — отдельный Python-процесс, который
подключается к комнате LiveKit и ведёт голосовой диалог. Внутри — конвейер из
трёх звеньев:

```
Речь клиента → STT → LLM (+RAG) → TTS → Голос аватара
              (Deepgram) (OpenAI)     (OpenAI/ElevenLabs)
```

1. **STT (Speech-to-Text)** — Deepgram Nova-3 переводит речь в текст (русский и
   др. языки).
2. **LLM** — OpenAI-модель генерирует ответ, но не «из головы», а опираясь на
   найденные факты компании (RAG, см. ниже).
3. **TTS (Text-to-Speech)** — OpenAI TTS (или ElevenLabs) озвучивает ответ.

Плюс по желанию — видео-аватар через **Lemon Slice**: «оживляет» фото лица,
синхронизируя губы со звуком. Если ключа нет — система работает в чисто голосовом
режиме. Это пример «деградации без поломки»: дорогая функция опциональна, базовая
работает всегда.

**Почему LiveKit, а не «самому собрать WebRTC»?** WebRTC — это ад из NAT,
ICE-кандидатов, TURN-серверов и потери пакетов. LiveKit берёт всё это на себя и
даёт готовый «Agents SDK», где конвейер STT→LLM→TTS собирается из готовых блоков.
Это экономит месяцы работы. LiveKit развёрнут self-hosted (свой сервер), чтобы не
зависеть от облака и не платить за минуты.

### 3.5. Хранилища данных — три разных, и каждое по делу

| Хранилище | Что хранит | Почему именно оно |
|-----------|-----------|-------------------|
| **PostgreSQL** | Компании, пользователи, диалоги, сообщения, документы (текст) | Надёжная реляционная БД для структурированных данных и связей. Стандарт индустрии. |
| **Qdrant** | Векторные представления (embeddings) кусочков документов | Специализированная векторная БД для семантического поиска — то, чего PostgreSQL не умеет «из коробки» быстро. |
| **Redis** | Кэш | Быстрая память для временных данных. |

**Почему два хранилища, а не одно?** PostgreSQL отлично хранит «факты» (вот
компания, вот её документ, вот диалог на 3 минуты). Но он не умеет искать
**по смыслу** — «найди кусочек текста, похожий по значению на вопрос клиента».
Это работа векторной БД Qdrant. Они дополняют друг друга, а не конкурируют.

## 4. Как работает RAG — сердце «умных» ответов

RAG (Retrieval-Augmented Generation, «генерация с поиском») — это техника,
которая заставляет LLM отвечать фактами **конкретной компании**, а не общими
знаниями из интернета. Без неё аватар стоматологии не знал бы её цен и расписания.

### 4.1. Загрузка знаний (происходит заранее, в фоне)

Когда админ загружает PDF/DOCX/TXT/CSV (`backend/knowledge/ingest.py`):

1. **Извлечение текста** — из файла достаётся чистый текст (для PDF — pypdf, для
   DOCX — python-docx, включая таблицы).
2. **Нарезка на кусочки (chunking)** — текст режется на фрагменты по ~400 слов с
   перекрытием в 40 слов. Перекрытие нужно, чтобы мысль не «разрывалась» ровно по
   границе кусочка.
3. **Векторизация (embeddings)** — каждый кусочек отправляется в OpenAI
   (`text-embedding-3-small`) и превращается в вектор из 1536 чисел. Этот вектор —
   «координата смысла» текста.
4. **Сохранение в Qdrant** — вектора кладутся в **отдельную коллекцию для каждой
   компании**: `company_<UUID>`.

**Ключевое решение — отдельная коллекция Qdrant на каждую компанию.** Это
гарантирует изоляцию: поиск по знаниям одной компании физически не может
зацепить данные другой. Просто и надёжно, без сложных фильтров.

**Почему загрузка идёт в фоне (background task)?** Векторизация большого файла
может занять секунды-минуты. Заставлять админа смотреть на крутящийся спиннер —
плохо. Поэтому backend мгновенно отвечает «принято», а реальная работа идёт в
фоне (`background_tasks.add_task`). В коде даже есть тонкость: документ
**коммитится в БД до** запуска фоновой задачи, потому что задача откроет свою
сессию БД и должна увидеть уже сохранённую строку.

### 4.2. Поиск во время разговора (происходит на каждую реплику)

Здесь — самое тонкое инженерное решение во всём проекте. Логика в
`agent/aigita_agent.py`, класс `RAGAgent`:

Перед каждым ответом LLM агент:

1. берёт последнюю фразу клиента;
2. превращает её в вектор (тем же OpenAI-эмбеддингом);
3. ищет в Qdrant 5 наиболее близких по смыслу кусочков знаний компании;
4. **подмешивает** их в контекст как system-сообщение: «Вот факты из базы знаний,
   используй их в ответе»;
5. только потом вызывает LLM.

Так LLM отвечает фактами компании, даже если они не были в исходном промпте.

**Почему поиск встроен в `llm_node`, а не в `on_user_turn_completed`?** Об этом
прямо написано в комментарии к коду, и это поучительная история. Сначала
разработчики повесили RAG на хук «реплика пользователя завершена»
(`on_user_turn_completed`). Но в LiveKit Agents 1.5.1 у этого хука есть куча
условий раннего выхода (пауза, слишком короткая фраза и т.д.), из-за чего в
проде он **просто не срабатывал**. Перенесли логику в `llm_node` — узел
конвейера, который **гарантированно** выполняется перед каждым вызовом LLM. Это
типичный пример «решение продиктовано реальностью библиотеки, а не теорией».

**Запасные варианты (graceful degradation):**

- Если в базе знаний ничего не нашлось, а вопрос «фактический» (про погоду, цену,
  время и т.п.) и включён веб-поиск — агент идёт в интернет через OpenAI
  Responses API (`web_search.py`).
- Любая ошибка RAG не валит разговор: функция поиска возвращает пустую строку, и
  LLM просто отвечает без дополнительного контекста. Принцип: **разговор важнее,
  чем идеальный ответ — никогда не падать молча в тишину**.

### 4.3. Самообучение аватара

Интересная фишка (`agent/memory_learning.py`): после каждого диалога, если у
компании включена память, агент извлекает пары «вопрос-ответ» и **дописывает их
обратно в Qdrant** как новые знания (с пометкой `source_type: learned`). Со
временем аватар «запоминает» удачные ответы и начинает отвечать на похожие
вопросы лучше.

Защиты от деградации:
- пары, где аватар сказал «не знаю», не сохраняются (есть список стоп-фраз);
- проверка на дубликаты по косинусной близости (порог 0.92) — чтобы база не
  распухала от почти одинаковых записей;
- обучение «дешёвое»: только эмбеддинги, без дополнительных вызовов LLM;
- запускается асинхронно после завершения диалога, не тормозя клиента.

## 5. Жизненный цикл одного разговора

Чтобы всё сложилось воедино, проследим путь от «клиент подошёл» до «аватар
ответил»:

1. **Открытие киоска.** Браузер грузит `/kiosk/<slug>` и запрашивает у backend
   конфиг компании (`GET /api/kiosk/<slug>/config`): имя, фото аватара,
   приветствие, подсказки-кнопки.

2. **Нажатие «Начать».** Браузер просит токен (`POST /api/kiosk/<slug>/token`).
   Backend здесь делает важную вещь: создаёт комнату в LiveKit и **зашивает в её
   metadata всю конфигурацию компании** — id, правила поведения, голос, ключи,
   настройки личности (`kiosk/router.py`). Возвращает JWT-токен и URL.

3. **Подключение.** Браузер по WebRTC соединяется с LiveKit, используя токен.

4. **Пробуждение агента.** LiveKit видит нового участника и запускает агента в
   комнате. Агент читает metadata комнаты — и мгновенно знает, какую компанию он
   сейчас представляет, каким голосом и характером говорить.

5. **Приветствие.** Агент здоровается (своей фразой или дефолтной для языка).

6. **Диалог.** Клиент говорит → Deepgram распознаёт → RAGAgent ищет факты в
   Qdrant → OpenAI формулирует ответ → TTS озвучивает → (опц.) Lemon Slice
   двигает губами. Параллельно `DialogTracker` пишет каждое сообщение в
   PostgreSQL.

7. **Завершение.** По тишине (idle timeout) или кнопке диалог закрывается. Агент
   записывает длительность, прибавляет минуты к счётчику компании
   (`minutes_used`), извлекает темы разговора и (если включено) запускает
   самообучение.

**Почему конфигурация передаётся через metadata комнаты, а не агент сам лезет в
БД?** Это делает агента почти **stateless** относительно бизнес-логики: вся нужная
информация приходит вместе с комнатой. Агент не обязан знать схему БД компаний,
не нужно держать лишние соединения. Backend — единственный «владелец» настроек, а
агент — их «получатель». Чистое разделение ответственности.

## 6. Почему именно такая инфраструктура

### 6.1. Docker Compose, а не Kubernetes

Вся система поднимается одной командой `docker compose up`. Для продукта,
который ставят на **один VPS** для одной компании (или для пилота), Kubernetes —
это стрельба из пушки по воробьям. Compose даёт всё необходимое: изоляцию
сервисов, сети, health-check'и, тома для данных — и при этом понятен любому.

Есть два файла: `docker-compose.yml` (база, для разработки) и
`docker-compose.prod.yml` (оверрайд для прода). Это стандартный приём: общая
конфигурация в одном месте, отличия прода (SSL, `network_mode: host`) — в другом.

### 6.2. `network_mode: host` для LiveKit и Agent в проде

Тонкий, но важный момент. WebRTC использует широкий диапазон UDP-портов
(50000–60000) для медиапотока. Прокидывать тысячи портов через Docker-сеть —
больно и медленно. Поэтому в проде LiveKit и агент работают в сетевом стеке хоста
напрямую (`network_mode: host`). Платой за это служит то, что агент обращается к
другим сервисам через `localhost`, а не по Docker-DNS — это явно учтено в
конфигурации и описано в README.

### 6.3. Миграции через Alembic, автоматически при старте

Скрипт `backend/start.sh` сначала прогоняет `alembic upgrade head` (применяет
миграции схемы БД), и только потом запускает сервер. Это значит: при каждом
деплое база сама приводится к нужной версии, без ручных шагов. История изменений
схемы видна в `alembic/versions/` — по именам файлов читается эволюция продукта
(добавили личность аватара, память, видео-настройки, демо-режим и т.д.).

### 6.4. Ключи API: глобальные с переопределением на компанию

Хитрое, но удобное решение. Ключи OpenAI/Deepgram/ElevenLabs можно задать
глобально (в `.env`), а можно — индивидуально для каждой компании (поля в таблице
`companies`). Агент использует правило «ключ компании → иначе глобальный ключ»
(`effective_..._key = user_key or settings.key`). Это позволяет либо
обслуживать всех на общих ключах владельца платформы, либо дать крупному клиенту
платить за свой расход самому. Гибко без усложнения кода.

## 7. Сквозные принципы, которые видны во всём коде

Если присмотреться, через весь проект проходят несколько повторяющихся идей:

- **Никогда не падать в тишину.** В голосовом продукте молчание = поломка.
  Поэтому RAG, веб-поиск, видео-аватар, самообучение — всё обёрнуто в `try/except`
  с безопасным «пустым» результатом. Лучше ответить без контекста, чем не ответить.

- **Дорогое и опциональное — отделено от базового.** Видео (Lemon Slice),
  ElevenLabs-голос, веб-поиск — всё включается по ключу/флагу. Нет ключа —
  система спокойно работает в упрощённом режиме.

- **Изоляция арендаторов на уровне хранилищ.** Отдельная Qdrant-коллекция на
  компанию, фильтрация по `owner_id`/`company_id` в backend.

- **Реальное время отделено от управления.** Тяжёлый трафик разговора идёт через
  LiveKit мимо backend; backend дёргается только на «контрольные точки» (выдать
  токен). Это позволяет масштабировать разговоры независимо от админки.

- **Тяжёлую работу — в фон.** Векторизация документов, самообучение, удаление
  чанков — фоновые задачи, чтобы пользовательские запросы отвечали мгновенно.

- **Простота как фича.** Ванильный фронтенд, Docker Compose, единый Nginx,
  доменная нарезка backend — всё выбрано так, чтобы один разработчик мог понять и
  развернуть систему целиком.

## 9. Краткое резюме

AIGITO — это **мультитенантная платформа голосового AI-аватара**, построенная
вокруг двух разделённых потоков: «управление» (HTTP/FastAPI/PostgreSQL) и
«разговор» (WebRTC/LiveKit/Agent). Умные ответы обеспечивает **RAG** поверх
векторной БД Qdrant с изоляцией по компаниям, а опциональные «премиум»-функции
(видео-аватар, кастомный голос, веб-поиск, самообучение) аккуратно отделены и
включаются по необходимости. Вся инфраструктура намеренно держится простой —
Docker Compose, один Nginx, ванильный фронтенд — чтобы продукт можно было
понять и развернуть малыми силами.
